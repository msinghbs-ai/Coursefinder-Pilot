# Working rules for this repository (CF-247)

These rules come from the Platform Admin and apply to every change.

- **G1: every background job is catalogued.** A scheduled job is listed in `pipeline.automation_catalogue` (or `pipeline.admin_job_kinds` for tasks).
- **G2: no operational value is written into code (v2.15.269, 13 Oct 2026: "make sure in future it's not getting hard coded").**
  - A job's size, a re-read or retry time, a threshold or a limit is a setting in `pipeline.platform_toolset_settings`.
    - Pipeline values use toolset `pipeline` and are read with `security.pipeline_num_v1(key, default)`.
    - Service values use their own toolset, read with `security.toolset_setting` or `security.fc_setting_num_v1`.
  - Every setting has a label, a range, a unit and a `used_by` line. It shows on Settings › Pipeline settings or Toolsets & limits, where it is changed with a reason.
  - Scheduled job commands never contain a number. They pass `security.pipeline_num_v1('batch.…', default)`.
  - Worker code reads settings through `svc_worker_settings_v1`.
  - Only technical safety values stay in code: claim and lease timers, fire guards, the month roll-over, and API time-outs. Each such line is marked `-- fixed: <why>`.
  - `tests/uat/cf-247-s32-controls-in-settings-contract.spec.mjs` fails any migration from `20261013012900` on that breaks this.
  - `security.controls_check_v1()` raises a notice for any running job that does.
- **G3: the consumer API is frozen (Decision 266, Platform Admin 18 Oct 2026: "From here on, make sure the consumer api are not affected by any decision or design").**
  - The consumer API is what the website and Zoho read: `public.website_v2_*`, `website_edge_*`, `website_api_v2_*`, `zoho_edge_*`, `svc_website_settings_v1`, every function in schema `api`, the tables and columns they read, and the edge functions `website-api-v2`, `wix-course-api`, `website-course-api`, `zoho-api-v2`, `zoho-course-api`.
  - No design or change may alter, drop, rename or retype any of it. New work reads from it or writes beside it (new tables, new columns), never into its shape.
  - A change that must touch it needs the Platform Admin's explicit approval, recorded as `-- Consumer API change approved: <who, when, why>` in the migration (and the edge function baseline in `tests/uat/consumer-api-baseline.json` updated), and re-takes the baseline with `security.consumer_api_rebaseline_v1`.
  - `tests/uat/cf-247-s57-consumer-api-frozen.spec.mjs` fails the build otherwise; job `consumer-api-guard` checks live daily and raises a hard flag on any drift.
- **Website API v2 (`website-search-v2`, Decisions 257 and 258) is additive only.** Nothing the website reads is renamed or removed; the provider Published switch decides what is returned; null means not held. Before changing anything the website reads, read `docs/integrations/WEBSITE-DEVELOPER-REQUIREMENTS.md` in the admin repo (requests, status, open work). Keep `tests/uat/cf-247-website-api-v2-contract.spec.mjs` and `cf-247-institution-type-contract.spec.mjs` passing, and reissue the developer guide when the API changes.
  - Developer documents (admin repo `docs/integrations/developer-pack/`) are for the website developer only (Platform Admin, 15 Oct 2026 17:24): they show how to use the API. Section 13 lists API changes only (a new field, filter, action or behaviour) against the previous issue. Platform fixes, data corrections and internal work are not described to the developer. Measured figures (section 8, examples, acceptance counts) are refreshed with each issue.
- **G4: tests are governed (Platform Admin, 26 Oct 2026).** Register: admin repo `docs/platform/TEST-REGISTER.md`, generated by `node scripts/test-register.mjs`.
  - Every spec starts with `// Guards: <rule or decision>`. The PR names it too. No anonymous tests.
  - A PR that adds, changes the guard of, or removes a test regenerates the register in the same change (doc-as-code).
  - A rule change that obsoletes tests retires them in the same PR, with the reason in the register's retirement log.
  - A rule with a central guard is not re-asserted in per-change specs: G2 is `s32`, G3 is `s57`, housekeeping and G1 are `s42`, the release contract is `m245`/`s70`.
  - Nothing is carried skipped or red. A skip for a missing environment belongs only to an `@deployed` spec, and the suite has no "known failures".
  - The phone viewport runs only `@responsive` tests and the deployed gate. Tag a test `@responsive` only when it checks behaviour at phone width.
  - `tests/uat/cf-247-s120-test-governance-contract.spec.mjs` fails the build otherwise. Quarterly prune with the docs budget; tests added, retired and net go in the Monday line.
- **Nothing is dropped or deleted by an applied migration.** Drops and deletes go to the Platform Admin as a paste file.
- **A passing qualification never switches anything on by itself.**
- Never create `package-lock.json`. Never commit the `node_modules` symlink.
- **Housekeeping (Decision 260, 15 Oct 2026; admin repo `docs/platform/DATA-PIPELINE-OPERATING-MODEL.md`).**
  - Every migration from `20261015030000` on has `-- Replaces:` and `-- Retires:` lines (or "nothing"), a `comment on table` for each new table, and a catalogue row for each new job. `tests/uat/cf-247-s42-housekeeping-contract.spec.mjs` fails the build otherwise.
  - A change that brings a new approach switches the old one off in the same change and marks it `retiring` in `pipeline.component_register` (with `replaced_by` and `retire_after`). Tables, functions and edge functions are dropped by a paste file after `hygiene.retire_after_days` (14), once nothing used them.
  - One-off probes and audits are not left deployed as edge functions. The weekly `hygiene-check` job and the daily Component register workflow keep the register current; the generated document is on the `component-register-snapshot` branch.
