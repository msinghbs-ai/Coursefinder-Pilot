# Working rules for this repository (CF-247)

These rules come from the Platform Admin and apply to every change.

- **G1: every background job is catalogued.** A scheduled job is listed in `pipeline.automation_catalogue` (or `pipeline.admin_job_kinds` for tasks).
- **G2: no operational value is written into code (v2.15.269, 13 Oct 2026: "make sure in future it's not getting hard coded").**
  - A job's size, a re-read or retry time, a threshold or a limit is a setting in `pipeline.platform_toolset_settings`.
    - Pipeline values use toolset `pipeline` and are read with `security.pipeline_num_v1(key, default)`.
    - Service values use their own toolset, read with `security.toolset_setting` or `security.fc_setting_num_v1`.
  - Every setting has a label, a range, a unit and a `used_by` line. It shows on Settings › Pipeline settings or Toolsets & limits, where it is changed with a reason.
  - Scheduled job commands never contain a number. They pass `security.pipeline_num_v1('batch.…', default)`.
  - Worker code reads settings through `svc_worker_settings_v1`.
  - Only technical safety values stay in code: claim and lease timers, fire guards, the month roll-over, and API time-outs. Each such line is marked `-- fixed: <why>`.
  - `tests/uat/cf-247-s32-controls-in-settings-contract.spec.mjs` fails any migration from `20261013012900` on that breaks this.
  - `security.controls_check_v1()` raises a notice for any running job that does.
- **G3: the consumer API is frozen (Decision 266, Platform Admin 18 Oct 2026: "From here on, make sure the consumer api are not affected by any decision or design").**
  - The consumer API is what the website and Zoho read: `public.website_v2_*`, `website_edge_*`, `website_api_v2_*`, `zoho_edge_*`, `svc_website_settings_v1`, every function in schema `api`, the tables and columns they read, and the edge functions `website-api-v2`, `wix-course-api`, `website-course-api`, `zoho-api-v2`, `zoho-course-api`.
  - No design or change may alter, drop, rename or retype any of it. New work reads from it or writes beside it (new tables, new columns), never into its shape.
  - A change that must touch it needs the Platform Admin's explicit approval, recorded as `-- Consumer API change approved: <who, when, why>` in the migration (and the edge function baseline in `tests/uat/consumer-api-baseline.json` updated), and re-takes the baseline with `security.consumer_api_rebaseline_v1`.
  - `tests/uat/cf-247-s57-consumer-api-frozen.spec.mjs` fails the build otherwise; job `consumer-api-guard` checks live daily and raises a hard flag on any drift.
  - **Website API v3 (Decision 277, Platform Admin 12 Nov 2026 21:00):** `website-api-v3` and `public.website_v3_*` are a separate copy beside v2 (R28 first). Until the website goes live on v3 it is open to additions and not part of the frozen surface; it only reads v2 and its data. At go-live the Platform Admin records the date and v3 joins this list, the baseline and `s57` in the same change.
- **Website API v2 (`website-search-v2`, Decisions 257 and 258) is additive only.** Nothing the website reads is renamed or removed; the provider Published switch decides what is returned; null means not held. Before changing anything the website reads, read `docs/integrations/WEBSITE-DEVELOPER-REQUIREMENTS.md` in the admin repo (requests, status, open work). Keep `tests/uat/cf-247-website-api-v2-contract.spec.mjs` and `cf-247-institution-type-contract.spec.mjs` passing, and reissue the developer guide when the API changes.
  - Developer documents (admin repo `docs/integrations/developer-pack/`) are for the website developer only (Platform Admin, 15 Oct 2026 17:24): they show how to use the API. Section 13 lists API changes only (a new field, filter, action or behaviour) against the previous issue. Platform fixes, data corrections and internal work are not described to the developer. Measured figures (section 8, examples, acceptance counts) are refreshed with each issue.
- **G4: tests are governed (Platform Admin, 26 Oct 2026).** Register: admin repo `docs/platform/TEST-REGISTER.md`, generated by `node scripts/test-register.mjs`.
  - Every spec starts with `// Guards: <rule or decision>`. The PR names it too. No anonymous tests.
  - A PR that adds, changes the guard of, or removes a test regenerates the register in the same change (doc-as-code).
  - A rule change that obsoletes tests retires them in the same PR, with the reason in the register's retirement log (written in `docs/test-retirement-log.md`; the register generator carries it).
  - A rule with a central guard is not re-asserted in per-change specs: G2 is `s32`, G3 is `s57`, housekeeping and G1 are `s42`, the release contract is `m245`/`s70`.
  - Nothing is carried skipped or red. A skip for a missing environment belongs only to an `@deployed` spec, and the suite has no "known failures".
  - The phone viewport runs only `@responsive` tests and the deployed gate; `@responsive` tests run on the phone project only and first assert they are at phone width. The screens operated from a phone (Course catalogue list, Course detail blade, Layer 4 Review) are guarded by `s121` (Platform Admin 26 Oct 2026 10:49).
  - A deployed test that changes live data or the UAT user's saved settings is tagged `@live-acting` (the register's "Acts on live" column). It runs only when the live-acting switch is on (weekly run: input or repository variable `DEPLOYED_WEEKLY_LIVE_ACTING`; `deployed-uat`: input). The switch is off by default. The weekly deployed run (`deployed-weekly.yml`, Monday 05:17) reports the safe specs run and the live-acting specs held separately.
  - `tests/uat/cf-247-s120-test-governance-contract.spec.mjs` fails the build otherwise. Quarterly prune with the docs budget; tests added, retired and net go in the Monday line.
- **Two repositories, one source of truth (Platform Admin, 16 Nov 2026 09:20).** This repository (Pilot) is code: migrations, edge functions, the frontend, scripts, tests and their fixtures, and documents a script generates and a spec guards (`docs/UI-MAP.md`, `docs/sops/`, release notes). The admin repository `msinghbs-ai/coursefinder-admin` is the live single source of truth for everything a person or a new session reads.
  - Not committed here from 16 Nov 2026: manual SQL paste files, audit or review reports (`claude/*.md` and the like), design and scope documents, and operational runbooks. They go to the admin repository: paste files to `docs/paste/`, audits and scope documents to `docs/platform/` (UI audits to `docs/platform/ui-audit/`), runbooks beside the existing ones in `docs/platform/`.
  - Every version bump, migration, or UI or scheduler change updates and merges its admin documents in the same release cycle: the design document, the Admin SOP mirror (`docs/sops/`), `docs/UI-MAP.md`, the paste file if there is one, the test register and the component (automation) register, and the current-state index `docs/CURRENT-STATE.md` (live migration head, active dispatchers, pending cutovers, open work). A release is not finished until the admin PR is merged and read back.
  - A new session starts from the admin `docs/CURRENT-STATE.md` and `docs/README.md`, then checks the live system; it does not rely on chat history.
  - Existing files (split 18 Nov 2026, Platform Admin approval 16 Nov 10:10): the paste files a spec, database fixture, workflow trigger or `scripts/test-evidence-classes.json` reads are test fixtures in `tests/fixtures/paste/` (byte for byte; guards unchanged). Every other paste file is in the admin repository's `docs/paste/` only. There is no `docs/paste/` folder here, and no new `PASTE-*.sql` is added outside `tests/fixtures/paste/` (`tests/uat/cf-247-s616-paste-files-one-source-contract.spec.mjs`). A new paste file for a person goes to admin `docs/paste/`; when a spec must read it, a byte-for-byte fixture copy goes to `tests/fixtures/paste/` in the same PR and the admin README lists its md5.
- **UI map and screen help (Platform Admin, 16 Nov 2026 09:04).** Map: `docs/UI-MAP.md`, generated by `node scripts/ui-map.mjs` from the menu (`src/nav-map.js`), the page switch (`pageBody` in `src/mature-main.jsx`) and each screen's component source. It lists every live admin route, top-level tab, sub-tab, fold and drawer. Never edit it by hand.
  - A PR that moves, renames or folds UI controls (a page, tab, sub-tab, card, fold, drawer or the control inside one) updates the inline screen help text for those controls (the words on the screen, and the in-app Guides and SOPs in `src/guide/` that name them) and regenerates `docs/UI-MAP.md` in the same release.
  - Every release bump runs `node scripts/ui-map.mjs --mirror <coursefinder-admin>` with the test register sync, and commits the mirror (admin `docs/UI-MAP.md`) with the register.
  - `tests/uat/cf-247-s557-ui-map-contract.spec.mjs` fails the build when the map and the screens disagree (`node scripts/ui-map.mjs --check` says the same locally). The generator stops rather than guess when it cannot place a tab's screen.
- **Nothing is dropped or deleted by an applied migration.** Drops and deletes go to the Platform Admin as a paste file.
- **A passing qualification never switches anything on by itself.**
- **On demand is not held by toolset limits; scheduled work is (Platform Admin 12 Nov 2026 21:07; admin operating model 3.3.2).** Only the account's own limits stop on-demand work (Firecrawl monthly plan and credit reserve, OpenRouter credit floor), plus policies that are not limits (directory sites, robots, manual locks, identity).
  - Work a Claude session asks for (a re-read, a re-attach, a fetch) is opened first with `security.on_demand_open_v1('claude_session', reason, provider_ids, estimate)`: tell the Platform Admin the estimate and the credit left it returns. Scope it to the work's Firecrawl purpose groups with `security.on_demand_scope_v1(id, groups)` (for example `{central}` for source discovery), so scheduled work of the same providers keeps its limits. When the work has run, close it with `security.on_demand_close_v1(id)` and report the actual use and the credit left.
- **AER v1 is frozen (Decision 276, Platform Admin 12 Nov 2026):** essential correctness and security fixes only; no new layout readers, word lists or recovery paths. New AER work goes to v2 (admin repo `docs/platform/AER-DESIGN-V2-PROPOSAL.md` v0.3, §9 amendments). Proven-structure readers (PDF cells, aligned grid) stay as v2 record sources.
- **Security documents and gates (Platform Admin, 20 Nov 2026, s808 to s810; ASD ISM September 2026).** The documents are in the admin repository, `docs/security/`: `ISM-SECURE-SDLC-AND-THREAT-MODEL.md` (lifecycle, environments Boost, Pilot and Production, people and AI roles, threat model), `AI-SYSTEM-CARDS.md` (AI inventory, spend limits, untrusted page text, provider data use) and `API-SECURITY-AND-EOL-GUIDE.md` (API authentication and errors, browser headers, versions and end of life). Update them in the same release as a change they describe.
  - **Page text read from a site is untrusted.** Any request that puts scraped text in front of a model wraps it with `fenceUntrusted` (`supabase/functions/coverage-sweep/untrusted.ts`), or at least `stripHiddenContent`. Prompt wording held in the prompt registry changes only by a registry version (spec `s553`).
  - **Model requests deny provider data collection (s811, ISM-2103).** Every OpenRouter request sets `provider: { data_collection: "deny", … }`; a stored routing can never switch it off (`tests/uat/cf-247-s811-ism-open-items-contract.spec.mjs`). Prompts that carry page text use `fenceSourceText` (`<untrusted_source_text>` tags) or `fenceUntrusted`.
  - **Public API errors never carry a raw database message.** Only fixed codes, the request id and the platform's own `INVALID_INPUT:` text.
  - **Gates:** `.github/workflows/security-gates.yml` runs a secret scan, a dependency audit and a CycloneDX SBOM on every pull request and push to main. The dependency jobs resolve a lockfile in the runner only; none is committed. `public/_headers` sets the browser security headers. Guard: `tests/uat/cf-247-s810-security-gates-contract.spec.mjs`.
- **Merging is automatic; never ask a person to merge or clean up (Platform Admin, 20 Nov 2026 17:00; s880).** Never stop and ask the user to merge a pull request or delete a branch.
  - **Admin first.** Merge the `coursefinder-admin` pull request before the Pilot one. Try `gh pr merge <n> --auto --squash --delete-branch`; when the session proxy refuses it (`HTTP 403`, GraphQL is blocked, and GitHub's own auto-merge is off in both repositories), add the `automerge` label instead (`gh pr edit <n> --add-label automerge`, or by REST `gh api repos/<owner>/<repo>/issues/<n>/labels -f "labels[]=automerge"`). Poll `gh pr view <n> --json state` (by REST `gh api repos/<owner>/<repo>/pulls/<n> --jq .merged`) until it is `MERGED` before touching Pilot.
  - **Then Pilot**, the same way, and wait until it is `MERGED` before the post-merge live checks and the Drive `Monitoring` sync.
  - **What the label does** (`.github/workflows/auto-merge.yml`, `scripts/ci/auto-merge.sh`, the same in both repositories): once the pull request is mergeable and every check is green (a new migration also needs the `live-dry-run` label and a successful `dry-run` check), it is squash-merged and its branch deleted. A failing check or a conflict stops the wait with a comment on the pull request; the next push or re-adding the label starts it again. A merge made by the workflow's `GITHUB_TOKEN` does not start push-to-main workflows, so in Pilot the script starts them: `Deploy on merge` (with the commits before and after the merge), `Security gates`, `Deployed UAT`, and `Release Currentness Deployed` when release files changed. Read the run summary to confirm the deploy ran.
  - **Probe branches.** Never leave a throwaway branch behind. A branch used only for rolled-back dry runs is named `…-probe` or `…-diag`; the Auto-merge workflow deletes it when its dry run finishes (no open pull request, no newer commit) and sweeps any `…-probe` branch idle for a day. Delete any other throwaway branch yourself when you are done with it.
- Never create `package-lock.json`. Never commit the `node_modules` symlink.
- **Housekeeping (Decision 260, 15 Oct 2026; admin repo `docs/platform/DATA-PIPELINE-OPERATING-MODEL.md`).**
  - Every migration from `20261015030000` on has `-- Replaces:` and `-- Retires:` lines (or "nothing"), a `comment on table` for each new table, and a catalogue row for each new job. `tests/uat/cf-247-s42-housekeeping-contract.spec.mjs` fails the build otherwise.
  - A change that brings a new approach switches the old one off in the same change and marks it `retiring` in `pipeline.component_register` (with `replaced_by` and `retire_after`). Tables, functions and edge functions are dropped by a paste file after `hygiene.retire_after_days` (14), once nothing used them.
  - **Cron dispatchers (Platform Admin 15 Nov 2026 22:36).** A deterministic dispatcher that takes over legacy scheduled jobs (for example `rollup-scheduler`, `admission-rule-runner`) registers each legacy job byte for byte with its own cron schedule and starts in shadow (it records what was due and runs nothing). After a **24-hour shadow cycle** whose report matches the legacy starts, the cutover makes the targets live and switches the legacy `cron.job` rows off (`active = false`) and marks them `retiring`; the `cron.unschedule` paste file is held for the 14-day retention window (`hygiene.retire_after_days`). A shadow or cutover change merges once GitHub CI is green and its rolled-back (`begin … rollback`) live dry run has passed; only its own targeted spec is run locally.
  - One-off probes and audits are not left deployed as edge functions. The weekly `hygiene-check` job and the daily Component register workflow keep the register current; the generated document is on the `component-register-snapshot` branch.

### Standing Mandate: Immediate Live Activation (No Unrequested Shadow or Future Deferrals)

Platform Admin, 21 Nov 2026 10:07 AEDT. Non-negotiable; it applies to every change in both repositories.

1. **Reported Bugs & Verified Fixes Ship Live Immediately:** Every reported bug fix, UI/filter fix, parser fix, or verified deterministic admission rule MUST take effect **immediately upon deploy** in the same PR.
2. **Zero Unrequested Shadow Soaks or Delayed Cutovers:** NEVER place a bug fix or verified admission rule into shadow-only mode, behind an off-by-default flag, or on a 24-hour / next-day cutover timer unless the user explicitly instructs a shadow period first.
3. **No Assumed Future Work:** NEVER defer a reported fix to "tomorrow", "a future lane", or "a follow-up PR" without explicit user confirmation. Either ship and activate the complete fix immediately in the current PR, or—if a hard guardrail conflict exists—ask the user for an immediate decision before writing deferred code.

### Standing Rule: Dynamic Database-Driven Lookups (No Static Lists or Cut Subsets)

Platform Admin, 21 Nov 2026 11:55 AEDT (S1-Dynamic-Lookups, s930). It applies to every change in both repositories.

1. **Every dropdown, filter option, pill set and picker reads the live database.** Providers, destination and source countries, study levels, campuses, qualifications, grade scales, English tests and bands, and currencies come from the `ref` tables and the live rows (active and Layer 4 pending), never from a list written into the code.
2. **No inner-joined or cut subsets.** A provider list holds every active provider (and any provider with rows of the kind shown), whatever it already has admitted. A list is never cut by an unordered `limit`; a long list is searched or paged on the server.
3. **Rolling years.** Intake-year lists and year-rollover rules use the current year (Melbourne time) to the setting `lookups.intake_years_ahead`, beside the years the data holds. No year is written into a filter or a rule.
4. **Shared source.** Screens read `public.admin_lookups_v1` through `src/lib/lookups.js` (`useLookups`), or the screen's own server read; coverage figures in the guide are read live, never typed. Guard: `tests/uat/cf-247-s930-dynamic-lookups-contract.spec.mjs`.

### Standing Rule: Self-Sustaining API & Key Governance (Independent Keys per Consumer and Version)

Platform Admin, 21 Nov 2026 13:11 AEDT (S1-RM-Design, s935). It applies to every change in both repositories.

1. **One key per (consumer, API version).** Every new API version, consumer endpoint, or key issue or rotation uses its own key, scoped to one consumer and one version. A key is never shared across versions or consumers. A new version signs in with `pipeline.api_key_auth_v1(platform, version, hash)` and logs with `pipeline.api_request_log_v1`, so its calls carry its own version and key.
2. **Registered in the database, shown with no screen change.** A new version is a row in `pipeline.api_versions` (platform, version, endpoint, key store, frozen), and its keys are rows in its key store (`private.api_keys`). Settings › API usage reads `public.admin_api_usage` › `versions` (`security.api_usage_versions_v1`): every version, each key's status (Active, Rotating / Grace, Not issued, Revoked), its masked prefix, created, rotated and last-used dates, and live 24 h / 7 d / 30 d usage (calls, 2xx, 4xx, 5xx, error rate, 95th-percentile time). A version or key the register does not name yet is listed too, marked "not registered". No version, key or count is written into the screen.
3. **Rotation without disruption.** Keys rotate with a dual-key overlap (`api.key_rotate_overlap_hours`): the new key is shown once; the old key keeps working as the previous key until the overlap ends. A new version's key starts "Not issued". Where a consumer already calls that version with an earlier version's key, that key works as its previous key for `api.new_key_bridge_days`, until the new key is issued.
4. **Guard.** `security.api_usage_coverage_v1()` lists any active registered version or key the read path misses; each change that adds one checks that it is empty. `tests/uat/cf-247-s935-api-usage-versions-keys-contract.spec.mjs` fails the build otherwise. A frozen version (G3) keeps its own sign-in; it is registered and shown, never changed.
