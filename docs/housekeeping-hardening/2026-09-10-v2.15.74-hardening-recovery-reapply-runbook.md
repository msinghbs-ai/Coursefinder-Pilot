### PIM contract that must be recreated exactly

The final contract enforced:

- `review_status='accepted'` only;
- current validity only (`valid_from <= current_date`, `valid_to >= current_date`, open bounds allowed);
- mandatory membership in the currently assigned family;
- family attribute must be visible;
- multivalue attributes preserve all accepted/effective rows;
- single-value attributes expose at most one preferred row **per `(attribute, locale, channel)` partition**;
- deterministic preferred-value tie-break;
- locale/channel partitions must remain separate where no request scope exists;
- nested `value_json` must preserve nested nulls, array nulls, JSON null, `0`, `false`, `{}` and `[]`;
- option labels use exact locale first, global/null locale fallback second, and never leak another locale;
- embedded option-label maps are per-value so one locale/channel cannot overwrite another;
- `course_description` is not dynamically duplicated when it is not a visible member of the assigned family.

### Important real-data observation

At the time of validation:

- Course registry: ~43,461.
- Existing retained PIM values: 163.
- All 163 were `course_description`.
- `course_description` was not a member of the assigned Course family.
- Therefore a known Course could correctly return family metadata with `pim_attribute_values: []`.

Do **not** “fix” an empty dynamic list by manufacturing values or relaxing family/review/validity semantics.

### Codex/review findings resolved in PR #46

The review loop identified and corrected issues covering:

- supplying PIM data into the runtime path;
- excluding expired values;
- preferred single-value semantics;
- restricting duplicate checks to the appropriate dynamic field context;
- accepted-only approval state;
- mandatory current-family membership;
- preservation of nested JSON null members;
- preservation of locale/channel partitions;
- per-value option-label map safety;

All published review threads were resolved before merge.
